## 1. Область и методика

**Проверено:** весь исходный код (`src/ValDoctor.Core`, `src/ValDoctor.App`), тесты, проектные файлы, `global.json`, GitHub Actions (`ci`, `build`, `release`, `codeql`), `dependabot.yml`, читаемые через API настройки репозитория, опубликованные релизы v0.1.0–v0.3.0 и история git.

**Методика:**
1. Модель угроз (раздел 2).
2. Три независимых ручных разбора по областям: граница привилегий и работа с hosts; сеть, TLS, DoH и обновления; CI/CD и цепочка поставки. Каждую находку я затем проверил сам.
3. Для каждой подтверждаемой находки — регрессионный тест. Все такие тесты **падали на исходном коде** и проходят после исправления.
4. Автоматические проверки:
   - анализаторы Roslyn с `AnalysisLevel=latest-all`: 0 предупреждений по безопасности (CA2xxx/CA3xxx/CA5xxx);
   - CodeQL `security-and-quality`: только замечания о качестве;
   - `dotnet list package --vulnerable --include-transitive`: уязвимых пакетов нет;
   - поиск секретов по всей истории git: не найдено;
   - сверка SHA закреплённых GitHub Actions с их тегами.
5. Повторное независимое ревью внесённых исправлений.
6. Проверка на настоящей сети: подбор адресов по-прежнему работает.

**Навыки (skills):**
- `security-review` — методика «поиск, затем отсев ложных срабатываний»;
- `code-review` — повторное ревью;
- `find-security-vulnerabilities-in-code` — изучен. Нужный ему инструмент Strix не установлен и требует Docker и ключ LLM, поэтому он не применялся; Docker-демон также не был запущен, и gitleaks/semgrep в контейнерах не запускались.

**Ограничения аудита:**
- Работа велась на macOS. Поведение Windows (NTFS reparse points, ReplaceFile, UAC, порядок поиска DLL, распаковка single-file) проанализировано по документации и смоделировано тестами, но не воспроизведено на Windows с Procmon.
- Динамическое тестирование (фаззинг на Windows, MITM-стенд) не проводилось.
- Код самой платформы .NET и Windows не аудировался.

## 2. Модель угроз

**Что защищаем:**
1. Целостность системного файла hosts: ничего кроме собственного блока для 6 доменов Riot, чужие строки сохраняются, возможен откат.
2. Границу привилегий: обычный процесс → UAC → повышенный помощник.
3. Корректность выбора адреса: нельзя закрепить адрес злоумышленника.
4. Происхождение распространяемого EXE.
5. Приватность: нет телеметрии и личных данных в журналах.

**Недоверенные источники:** системный DNS и вся сеть (ради враждебной сети программа и существует); ответы DoH и GitHub API; содержимое hosts (могут писать другие программы с правами администратора); файлы в `%LocalAppData%` и `%TEMP%` (доступны любой программе пользователя); аргументы командной строки помощника; переменные окружения пользователя (`HKCU\Environment` наследуется повышенным процессом).

**Злоумышленники:**
- A1 — враждебная сеть (провайдер, роутер, Wi-Fi, подмена DNS);
- A2 — вредоносная программа с правами того же пользователя без прав администратора;
- A3 — тот, кто получил доступ на запись в GitHub-репозиторий;
- A4 — подменённая копия EXE у зеркала или в чате.

**Вне модели:** злоумышленник, уже имеющий права администратора или SYSTEM; уязвимости самой Windows и .NET.

## 4. Находки

### High

**H1. Любой, у кого есть право записи, может выпустить вредоносный релиз, о котором сообщат все установленные копии** — *требует решения*
- **Где:** настройки репозитория и `.github/workflows/release.yml`.
- **Проверенные факты:** для `main` нет правил защиты и rulesets; тег `v*` может создать любой участник с правом записи; у второго участника `FIXAzz` есть право записи; неизменяемые релизы выключены; secret scanning и push protection выключены.
- **Сценарий (A3):** украденный токен или скомпрометированная учётная запись → тег `v0.3.1` (workflow берётся из помеченного коммита) или замена файлов существующего релиза. Встроенная проверка обновлений покажет уведомление всем пользователям, а EXE затем попросит права администратора. Файл `.sha256` рядом с EXE не защищает: злоумышленник подменяет оба.
- **Рекомендация (это настройки, а не код — выполняете вы):**
  1. Убрать лишний доступ на запись или обосновать его; включить 2FA.
  2. Ruleset для `main`: только через PR, без force-push и удаления.
  3. Ruleset для тегов `v*`: создавать и изменять может только администратор.
  4. Включить неизменяемые релизы (immutable releases).
  5. Окружение `release` с обязательным подтверждением.
  6. Включить secret scanning и Dependabot alerts.

### Medium

**M1. Адрес, известный только системному DNS, мог быть закреплён в hosts** — *исправлено*
- **Где:** `Diagnostics/DiagnosticsEngine.cs` (кандидаты из системного DNS), `Diagnostics/DiagnosisModels.cs` (`BestCandidate`).
- **Сценарий (A1):** враждебный DNS отвечает `[ретранслятор, «мёртвый» адрес]`. Ретранслятор TCP-прокси пробрасывает соединение к настоящему серверу Riot, поэтому сертификат подлинный. Сервис выглядит нестабильным → ValDoctor закрепляет адрес ретранслятора, и запись остаётся после ухода из этой сети. Злоумышленник получает постоянную позицию на пути трафика: метаданные и возможность обрыва соединения; содержимое по-прежнему защищено TLS.
- **Исправление:**
  - закрепляется только кандидат, которого вернул хотя бы один доверенный DoH-резолвер (`CandidateEvidence.ConfirmedByTrustedDns`); если DoH недоступен, исправление не предлагается;
  - по итогам повторного ревью: адреса, известные только системному DNS, больше не занимают ограниченные места среди кандидатов.
- **Тесты:** `M1_*` (5 случаев).

**M2. Поддельные строки `# valdoctor-off:` / `# riotfix-off:` превращались в активные записи для любых доменов** — *исправлено*
- **Где:** `Hosts/HostsDocument.cs` `TryParseDisabled` (используется в `SetPins` и `RevertAll`).
- **Сценарий:** метка — хеш без ключа, её легко подделать. Комментарий `# valdoctor-off:<hash> 10.0.0.66 www.paypal.com`, подложенный в hosts (сторонним инструментом, импортом списка блокировок, при ослабленных правах доступа), при любом «Исправить» или «Отменить изменения» становился активной записью для домена, не относящегося к Riot.
- **Исправление:** строка считается отключённой ValDoctor/RiotFix, только если это корректная запись и **все** имена в ней из списка Riot. Ни RiotFix 0.1.0–0.2.1, ни ValDoctor другие строки никогда не отключали, поэтому совместимость сохранена.
- **Тесты:** `M2_*` (4 случая, включая сохранение настоящих строк RiotFix).

**M3. Сбой ReplaceFile мог оставить систему без файла hosts** — *исправлено*
- **Где:** `Hosts/HostsFileService.cs`.
- **Сценарий:** при ошибке `ERROR_UNABLE_TO_MOVE_REPLACEMENT` (1176) Windows уже удалила hosts, а новый файл остался под временным именем. Обработчик ошибки удалял временный файл, и hosts пропадал целиком вместе с чужими записями пользователя.
- **Исправление:** при любой ошибке, если hosts исчез, восстанавливается его прежнее содержимое (`RestoreIfHostsMissing`); временный файл удаляется только после этого.
- **Тест:** `M3_*`.

**M4. Нет доказательства происхождения сборки; проверка по хешу рядом с файлом** — *требует решения*
- **Проблема:** EXE не подписан, attestation о происхождении сборки (build provenance) нет. Пользователей учат проходить предупреждение SmartScreen. Файл SHA-256 лежит рядом с EXE и не защищает от подмены релиза (H1) или зеркала (A4).
- **Рекомендация:** добавить `actions/attest-build-provenance` и проверку `gh attestation verify ValDoctor.exe -R IskhakovMA/riotfix`; затем подпись через SignPath (PR #6). Сейчас не внедрено: это изменение Release workflow, по условиям задачи требуется отдельное решение.

**M5. Ранее закреплённые адреса не сверялись с доверенным DNS** — *обнаружение добавлено, замена требует решения*
- **Найдено при повторном ревью исправлений.**
- **Проблема:** адрес, закреплённый раньше (в том числе RiotFix 0.2.0–0.2.1 или ValDoctor 0.3.0 до исправления M1), разрешается в сам себя и проходит проверку. Поэтому он навсегда выглядит здоровым, и DoH для него не опрашивается.
- **Сделано:** для закреплённых доменов ValDoctor теперь опрашивает DoH. Если ни один резолвер не возвращает закреплённый адрес, в «Подробностях» и в журнале появляется предупреждение с советом нажать «Отменить изменения». Тесты `M1_existing_pin_*`.
- **Требует решения:** автоматически предлагать замену такой записи подтверждённым адресом. Это меняет поведение: рабочая запись, из которой адрес выпал при смене адресов Cloudflare, начнёт показываться как «Обнаружена проблема с подключением». Поэтому без вашего согласования не внедрено.

### Low

**L1. Блокировка во время замены файла теряла параллельное изменение другой программы** — *исправлено*
Повтор `Replace` после блокировки шёл без повторного чтения файла. Теперь попытка начинается заново со свежего чтения и проверки (`MaxAttempts = 5`). Тест `L1_*`.

**L2. Исходная резервная копия записывалась неатомарно** — *исправлено*
При сбое питания оставалась усечённая «исходная» копия, которая больше никогда не перезаписывалась. Теперь копия пишется во временный файл и переименовывается. Тест `L2_*`.

**L3. Внедрение кода в повышенный процесс до `Main` (A2)** — *частично исправлено, остальное — ограничение*
- **Исправлено:** `StartupHookSupport=false` — переменная `DOTNET_STARTUP_HOOKS` из `HKCU\Environment` больше не действует. DNS-кэш очищается через `ipconfig.exe` по абсолютному пути: `dnsapi.dll` по имени больше не загружается, поэтому подложенная DLL в папке загрузок или распаковки не подхватится. Тест `L3_*`.
- **Осталось:**
  - переменные профилировщика CoreCLR (`CORECLR_ENABLE_PROFILING`/`CORECLR_PROFILER_PATH`) и диагностики (`DOTNET_EnableEventPipe`, `DOTNET_DbgMiniDumpName`), которые повышенный процесс наследует из `HKCU\Environment`;
  - папка распаковки single-file в `%TEMP%`, содержимое которой не проверяется на целостность;
  - окно, запущенное от администратора, не ограничивает поиск DLL: иначе WPF не загрузит свои распакованные библиотеки. Пока EXE не подписан и лежит в «Загрузках», тот же злоумышленник может просто подменить сам EXE, так что практический выигрыш атаки сейчас невелик. Значение вырастет после подписи. Предложение: маленький отдельный помощник без WPF (без распаковки) и подпись — отдельная задача.

**L4. Окно, запущенное от администратора, писало и удаляло файлы в `%LocalAppData%`** — *исправлено*
Через junction-точки это давало произвольное удаление или запись с правами администратора. Теперь при запуске от администратора журнал не пишется (`NullLog`), а состояние проверки обновлений хранится только в памяти. Тест `L4_*`. Побочный эффект: при запуске «от имени администратора» файлы журналов не создаются.

**L5. Доверие держится только на корневом хранилище сертификатов Windows, отзыв не проверяется** — *принято как ограничение*
Корневой сертификат, установленный пользователем или средой (корпоративная инспекция TLS, национальные удостоверяющие центры), позволит подделать и DoH, и сертификаты Riot. Проверка отзыва выключена так же, как по умолчанию в .NET HttpClient. Предложение на будущее: закрепить открытые ключи DoH-резолверов или ограничить список корневых центров.

**L6. Проверка символических ссылок выполняется до открытия файла; права на `drivers\etc` не проверяются** — *принято как ограничение*
По умолчанию писать в каталог может только администратор, поэтому атака требует заранее ослабленных прав. Предложение: проверять ACL каталога и открывать файлы с `FILE_FLAG_OPEN_REPARSE_POINT`.

**L7. Нет ограничения времени между последней перепроверкой и записью после UAC** — *принято как ограничение*
Окно UAC может висеть сколь угодно долго. Последствие — только доступность: адрес проверен, повторная проверка после записи покажет проблему, а откат доступен.

**L8. SDK и runtime в EXE «плавают» вместе с образом раннера** (`global.json` `rollForward: latestFeature`) — *требует решения*
Бинарник нельзя воспроизвести байт-в-байт. Рекомендация: закрепить точную версию SDK и обновлять её через Dependabot.

**L9. Тестовые пакеты NuGet выполняются в той же задаче, что собирает EXE; нет lock-файлов** — *требует решения*
Рекомендация: `RestorePackagesWithLockFile` и `--locked-mode`; отдельная задача для публикации.

**L10. Не включены функции безопасности GitHub; закрепление по SHA не обязательно** — *требует решения*
Нужно включить secret scanning, push protection и Dependabot alerts, а также `sha_pinning_required`. Dependabot PR #1/#2 указывают на старый путь `tests/RiotFix.Core.Tests`.

### Informational

**I1. Строка с правильной меткой, но с непубличным адресом считалась своей** — *исправлено*
Например, `0.0.0.0 auth.riotgames.com # valdoctor:…`. Теперь такая строка не принадлежит ValDoctor и не удаляется при откате. Тест `I1_*`.

**I2. Текст уведомления из файла состояния показывался без очистки** — *исправлено*
Ссылка и раньше строилась только из проверенного тега. Теперь заголовок и описание очищаются и обрезаются так же, как данные GitHub. Тест `I2_*`.

**I3. Не все служебные диапазоны IP считались непубличными** — *исправлено*
Добавлены `3fff::/20`, `2001:2::/48` и `2001:10::/28`. По итогам повторного ревью исправлена маска `3fff::/20`: первоначальная правка ошибочно закрывала `3ff0::/12`. Диапазоны, которые IANA помечает как глобально достижимые (AS112, AMT, ORCHIDv2), исключать не стали. Тест `I3_*` проверяет и границы диапазонов.

**I4. Неточный комментарий о приватности журнала и неэкранированный текст в отчёте** — *комментарий исправлен, остальное принято*
Комментарий утверждал, что локальные адреса не пишутся, хотя DNS-ответы с адресами-заглушками пишутся. Имя издателя сертификата, которое контролирует сервер, попадает в копируемый отчёт без экранирования: это только подмена текста в отчёте.

**I5. Закреплённые адреса никогда не устаревают** — *принято*
Затрагивает только доступность. Повторная проверка заменяет неработающий адрес проверенным.

**I6. Нестандартный `DataBasePath` молча заменяется стандартным путём** — *принято*
С точки зрения безопасности это безопасный отказ.

**I8. Поддельная «отключённая» строка только с доменами Riot по-прежнему восстанавливается при откате** — *принято*
Чтобы её подложить, нужно право записи в hosts, то есть права администратора. Активная запись указывает на адрес, который не пройдёт проверку TLS для домена Riot.

**I7. `release.yml` отрезает суффикс предварительной версии от номера сборки** — *требует решения*
Сейчас не используется: все теги вида `v0.x.y`.

## 6. Проверено и признано надёжным

- **Протокол повышенного помощника:** только точные токены, разрешённые домены, строгий разбор IP (без сокращённой записи, ведущих нулей и зон), только публичные адреса, без дубликатов. Через `ShellExecute` нечего внедрить. Путь к hosts берётся из HKLM без раскрытия переменных и из системного API. Помощник ничего не пишет в профиль пользователя.
- **hosts:** чужие байты сохраняются (200 000 случайных файлов при проверке аудитора), отключаются только строки, где все имена из списка Riot, работает откат, совместимость с RiotFix сохранена.
- **TLS:** принимается только `SslPolicyErrors.None`, SNI равен проверяемому домену, у каждого этапа есть таймаут.
- **Разбор DNS:** проверка границ, ограничения на указатели, длину и цепочку CNAME.
- **Проверка обновлений:** размер ограничен после распаковки, глубина JSON ограничена, перенаправление допускается одно и только на `api.github.com`, ссылка строится из проверенного тега, ничего не скачивается и не запускается.
- **GitHub Actions:** минимальные права, все actions закреплены по SHA (сверено с тегами), нет `pull_request_target`, нет внедрения в `run:`, нет кэшей и секретов, артефакты читаются только из текущего запуска.
- **Зависимости:** приложение не использует пакетов NuGet; в тестах — xUnit и Test SDK без известных уязвимостей.

## 7. Итоговая оценка

ValDoctor 0.3.0 с исправлениями из этой ветки подходит для **ограниченного** распространения (prerelease) пользователям, которые понимают, что EXE не подписан. Для широкого распространения сначала нужно:
1. Закрыть H1 настройками репозитория.
2. Добавить provenance и подпись (M4).
3. Решить вопрос замены непроверенных старых записей (M5).
4. Подтвердить работу помощника на Windows через Procmon (L3).

Программа не является «абсолютно безопасной». Её защита основана на том, что пользователь запускает подлинный EXE, а Windows и платформа .NET работают корректно.
